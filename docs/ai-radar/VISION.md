# ai-radar · 产品愿景与阶段路线图

> 状态：v0.1 草案 (2026-05-07)
> 维护者：lindong
> 范围：本文档为**愿景章程 + 阶段路线图**，不包含任何 phase 的实现细节；每个 phase 单独写 PRD/plan。

---

## §1. 一句话定位

`ai-radar` 是一个**单用户管理、公开只读浏览**的 AI 信息雷达。从 owner 预设的 RSS 信源池里抓取条目，经多维 LLM 评分 + 代码化权重计算 + 事件聚类，输出每日少量高价值精选；通过 Web 时间线和精选页消费，长期演进出 IM 推送、日报、反馈学习与趋势洞察。

参照锚点：[AIHOT](https://aihot.virxact.com/) (作者：数字生命卡兹克)。本产品复用其踩坑经验与核心机制，但定位从"AI 自媒体的选题工具"转为"工程师视角的个人信息消费工具"。

## §2. 目标用户与使用场景

### 用户角色

| 角色 | 写权限 | 读权限 | 数量 |
|---|---|---|---|
| **Owner** (lindong) | ✅ 信源管理、反馈打标、规则调权 | ✅ 全量 | 1 |
| **Public visitor** (匿名) | ❌ | ✅ 全公开页面，无 tab/字段隐藏 | 任意 |

### 核心场景

1. **晨起扫精选 (5 分钟)** — Owner 打开 web，看精选 tab，过滤掉昨夜 RSS 噪音。
2. **碎片时间深读** — 点击精选条目跳到原文。
3. **反馈打标** — Owner 给条目 👍/👎 + 可选文字注释，喂入回归评估系统。
4. **信源管理** — Owner 增删改信源 / 调级 (T1 / T1.5 / T2) / 改启停。
5. **公开访问者浏览** — 任意人无登录访问 web，看到与 owner 完全一致的精选/时间线 (仅按钮/写表单不存在)。
6. **(v2+) IM 推送消费** — Owner 在 Telegram 里被动接收每日精选。

### 非用户/非场景 (排除)

- 不服务"想发现新信源"的用户 — 信源由 owner 手动管理，系统不做信源推荐。
- 不服务"想搜索 AI 历史"的用户 — 这是流式消费工具，不是搜索引擎。
- 不服务内容创作者 — 不输出选题角度、不生成观点、不做 SEO。

## §3. 与 AIHOT 的同/异

### 同 (复用)

- 信源分级思想 (T1 / T1.5 / T2 与精选权重挂钩)
- 5 维 LLM 评分 + 代码化权重计算 + 阈值精选 (反对"全交给 LLM 给最终分")
- Embedding 事件聚类 + 官方源优先选主条
- 人类反馈 + 自动回归评估 (重新评估过去 N 条新闻验证规则迭代)
- 时间线/精选/日报三段式 UI
- 便宜模型预筛 + 贵模型评分的成本分层

### 异 (差异化)

| 维度 | AIHOT | ai-radar |
|---|---|---|
| 写入用户 | MCN 团队 + 签约博主 | Owner 一人 |
| 工作目标 | 找选题 / 辅助创作 | 日常消费 / 节省注意力 |
| 评分权重偏向 | 自媒体口味 (流量、传播性) | 工程师口味 (工程实践、工具链、模型工程) |
| IM 推送 | 无 | v2+ 有 (Telegram) |
| 信源接入 | RSS + 爬虫 + Twitter API + 第三方付费 | RSS-only 起步，其他能力进路线图 |
| 实现 | 内部闭源 | greenfield 自建 (明确不复用本仓库现有 summary-agent) |
| 双版本 | 内部版 vs 公开版内容不同 | 公开 = 内部，仅写入口隐藏 |

## §4. 核心原则 (BINDING)

这五条决定了所有后续 phase 的设计取舍。任何 PRD/plan 与之冲突时，原则优先。

### 1. 能用脚本就别用 LLM

LLM 只输出**结构化的 5 维分**；权重计算、阈值判断、排序、聚类、去重一律用代码实现。

**理由**：AIHOT 在 V7→V8 尝试让 LLM 同时打分/打权重/判类别，全面回滚。规则越多，模型泛化能力越差；最终把 LLM 职责砍到 5 维评分后，prompt 从 600 行缩到 200 行，质量反而上升。

**应用**：评分 prompt 严禁要求 LLM 输出"是否精选"或"最终分"。所有可被代码确定性计算的逻辑必须代码化。

### 2. Precision ≫ Recall

宁缺毋滥。每天精选 < 30 条 (AIHOT 体感量级)；漏掉一些边缘价值条目 OK，让噪音进入精选页不 OK。

**理由**：注意力是稀缺资源，工具的价值在于过滤而非汇总。Recall 提升的边际价值很快归零，Precision 下降的代价立刻反映在"我又不想打开了"。

**应用**：阈值默认偏严；UI 不做"展开更多"那种隐式 recall 通道。

### 3. 可回测、可对比

每次评分规则升级 (prompt 改、权重改、阈值改)，必须能在过去 N 天的存量数据上跑回归对比，输出新旧版本对每条数据的差异。否则不上线。

**理由**：单户场景没有 A/B 实验的统计基础，回归对比是唯一可信的"是不是变好了"验证手段。

**应用**：原始抓取数据、每次评分中间结果、最终精选名单都需持久化。规则版本号是数据 schema 的一部分。

### 4. 反馈闭环但不过拟合

反馈数据用于调整**代码侧的权重和阈值**，不用于 fine-tune 模型本身，也不用于把规则塞进 prompt。

**理由**：单户反馈样本极小 (一天最多几十条)，fine-tune 必过拟合；prompt 加规则会重蹈 AIHOT V7→V8 覆辙。

**应用**：反馈进数据库，权重调整有 review 流程 (你自己 review)，不自动触发模型训练。

### 5. 数据是资产，逻辑是燃料

抓取到的原文、评分中间结果、反馈、规则版本号永久持久化。评分逻辑可以推倒重写，数据不能。

**理由**：数据丢了不可逆；逻辑写错了下次能改。schema 设计要为"逻辑会被重构 N 次"做准备，不要把当下的某版评分细节绑进核心 schema。

**应用**：核心表 (条目、评分、反馈) 的 schema 保守宽松；版本特定字段进 JSON blob 不进列。

## §5. 反例 (明确不做的事)

| 反例 | 理由 |
|---|---|
| 不做多用户写 | 单户即终态；保持简单 |
| 不做信源发现 / 推荐 | Owner 手动管理是设计选择，非限制 |
| 不做内容生产 / 选题辅助 | 这是消费工具不是创作工具 |
| 不做实时 (秒级) 推送 | v0 不做；v2+ IM 推送也是批量节奏 (例：早 8 点) |
| 不做 GPU 部署 / 不做本地大模型 | 评分一律走 API，便宜模型够用就用 |
| 不做需要登录的浏览体验 | 公开页面零鉴权，写入口走 admin token / IP 白名单 |
| 不做内部版与公开版的内容差异 | 你看到什么公众看到什么；只在写入口区分 |
| 明确不复用 ai-assistant 仓库现有 summary-agent 基础设施 | 本次会话的明示选择，理由待 owner 后续补充至 §10 |

## §6. 成功指标

成功定义采用三轴并行 (任一轴掉线都说明产品退化)：

### A 行为指标 (可量化、可被 gaming，但容易看)

- Owner 每日打开 web ≥ 80% (周聚合)
- 精选条目点击跳转率 ≥ 30%
- Owner 每周给出反馈 ≥ 5 条

### B 信号指标 (直接衡量产品价值，需主观打标)

- 漏报：Owner 通过其他渠道知道但精选没收录的"重要事件" ≤ 1 件/周
- 噪音：精选条目里 Owner 标 👎 的比例 ≤ 10%

### C 时间指标 (衡量"它节省了我多少时间")

- 每日扫描时间 ≤ 5 分钟
- 每月维护信源/调规则的时间 ≤ 1 小时

> 三轴互相牵制：A 高但 B 差 = 你出于习惯打开但内容差；B 好但 C 差 = 内容好但维护成本高。

## §7. 能力地图

下面是产品长期可能涉及的能力清单 (capability map)，路线图从这里挑切片。本节**不**承诺时间。

### 数据层

- 信源管理 (注册、分级、启停、批量导入)
- RSS 抓取 + 调度
- (后续) 爬虫 / X API / 公开 API / 公众号
- 原文持久化、去重 (URL/内容指纹)
- 信源健康监控 (失效率、延迟)

### 评估层

- AI 相关性预筛 (便宜模型)
- 多维 LLM 评分 (5 维或更多)
- 代码权重公式 + 阈值精选
- Embedding 事件聚类 + 主条选择
- 规则版本管理 + 回归评估系统

### 反馈层

- Owner 反馈打标 (👍/👎/comment)
- 反馈 → 权重调节面板
- 反馈数据集导出 (用于回归)

### 消费层

- Web 时间线 (实时流)
- Web 精选页 (高分 + 聚类后)
- 每日报 (按版块整理)
- IM 推送 (Telegram)
- 跨设备体验 (移动浏览器即可，不做原生 app)

### 洞察层 (远期)

- 趋势预测 (加速曲线检测)
- 实体热度指数
- 历史关联拽取 (此事件过去一个月的相关条目)
- 主题/兴趣权重调节 UI

## §9. 风险与未决项

### 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| LLM 评分稳定性 (AIHOT V11 才稳) | v0 很可能"评分不准就打开率低" | v0 完成后立刻进入 1-2 周纯调参期，不急着做 v1 |
| 单户反馈样本不足导致过拟合 | v1 反馈调权时被几条强反馈带偏 | 原则 §4.4；权重调整需 review，不自动应用 |
| RSS 信源失效或被改版 | 数据断流 | v1 加信源健康监控；信源出错时降级到上次成功值 |
| 数据 schema 写死带来迁移成本 | 任何 schema 变更需要写脚本迁移历史数据 | 原则 §4.5 ；版本特定字段进 JSON blob |
| 副业项目精力空窗期 | 几周不维护会信源失效堆积 | 自动失效告警；对失效信源默认禁用而非删除 |

### 未决项 (本文档不解决，留给 PRD)

- 部署位置 (本地 / 自有服务器 / 云)
- 数据库选型 (sqlite / postgres / 文件 + index)
- Web 框架选型 (Next.js / FastAPI + 静态前端 / 其他)
- LLM 评分模型具体选型 (DeepSeek V4 Pro / Sonnet 4.6 / Haiku 4.5)
- 公开 web 域名 (`virxact.com` 那种公司域名 vs 个人域名 vs 子域)
- Telegram bot 权限模型 (公开命令 vs owner-only)
- Owner 反馈 UI 形态 (浏览器扩展 / web 内嵌 / Telegram inline)

## 附录 A. 术语

- **精选** — 经评分 + 阈值过滤后值得 owner 看的条目子集
- **主条** — embedding 聚类后被选作"代表"的条目；其他相关报道折叠在它下面
- **5 维评分** — LLM 输出的 5 个维度分数 (具体维度在 v1 PRD 定义)
- **回归评估** — 用新版评分规则在历史数据上重跑，对比新旧版本差异
- **T1 / T1.5 / T2** — 信源权重等级 (T1 = 一手官方源，T1.5 = 官方社交账号，T2 = 个人/媒体/聚合)
