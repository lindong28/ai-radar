# 原始数据、参照输出与题集派生

> [Developer] · Mutable snapshot · 2026-09-16 · 前置定义提案。本文定义准入与建题依据，不宣称已经得到连续合格数据集。总入口见 [README](README.md)。

## 1. 三种数据分开

| 数据层 | 权威来源与内容 | 本次用途 | 不可替代的东西 |
|---|---|---|---|
| Radar 原始输入 | `data/raw-capture/runs/<run-id>/manifest.json` 与 `items.jsonl.gz`，真实 fetch 在 upsert/prefilter 之前保存的 `FetchedItem` | 共同来源的完整候选输入、同文不同版本与观察时序 | 不能拿处理后的 `items`、截断 prompt 或旧 T5 替代 |
| AIHOT 参照 | `benchmarks/aihot` 中 capture/window、API 原始响应、SSR 原文、规范化条目及其证据定位 | 页面可见字段和可见集合的参考输出 | API 字段存在不证明页面可见；捕获成功不证明所有页面都已归档 |
| 诊断/运行状态 | 当前 `radar.db`、采集 outbox、旧 runs、历史报告 | 解释代码、阶段状态和历史失败 | 不作为新 raw/gold，不回填缺失的历史原始输入 |

原始输入指系统实际收到的解析结果，不声称保存了全网文章全集或每条来源的完整 HTTP 原始报文。`FetchedItem` 正文可以是源提供的摘录，不能改名成“完整原文”。正文补全若发生在归档前，归档的是该次补全后的输入；具体长度与内容以留档字节为准。

[归档实现](../../../src/airadar/fetcher/raw_capture.py) 校验压缩 payload 哈希、行数、逐源计数和记录结构；[抓取入口](../../../src/airadar/fetcher/runner.py) 提供真实采集边界。评测派生不修改这些原始文件。

## 2. 时间窗与三个时钟

用户最初指定的期望窗是 `[2026-09-06T00:00:00+08:00, 2026-09-14T00:00:00+08:00)`，即 9/06—9/13 共 8 个本地自然日、192 小时，不是 7 天。先检查该窗内两侧证据，再找连续合格子窗；不足时不拼接不连续时段来凑够天数。

| 时钟 | 含义 | 决定什么 |
|---|---|---|
| 来源发布时钟 | 原文 `published_at`，可能陈旧、缺失或经抓取器修正 | 新闻年龄和列表排序的输入；不证明何时取得输入 |
| 产品归窗时钟 | AIHOT 的 discovered/published 字段及其窗口规则；Radar 自己的业务时间字段 | 某条新闻属于哪个参照窗口/页面状态 |
| 我方观察时钟 | Radar 的 run/逐源观察时刻、AIHOT 的 API/SSR 捕获时刻及响应时间证据 | 原始输入何时实际可用，观察到的是哪版输出，以及采集是否连续 |

AIHOT 现有 [timeline_key](../../../src/airadar/eval/aihot_dataset.py) 通常取 discovered 时间，但当 published 存在且比 discovered 早超过 72 小时时回退到 published。保留 capture/window 原来的归窗身份，不把它简单改述为“按捕获时刻”或“只按 discoveredAt”。这也不自动成为新评测全部问题的唯一归窗规则。

配对时同时保留这三个时钟。后捕获的页面可能展示早先发现的新闻及更新后的文案；当天完整 API 日窗不等于当天每一刻的页面状态都可重放。不得用 `published_at` 首尾或最早/最晚抓取差值冒充连续覆盖时长。

## 3. 先确定共同来源池 S

共同来源的最低证据是在拟使用时间窗内，AIHOT 至少出现一次能明确归属该源的条目；还需核对入口与语义相同，例如直读原站、Hacker News 聚合、转述源并非因为指向同一 URL 就是同一个输入源。

| 来源情况 | 本次处置 |
|---|---|
| 两侧源身份、入口语义已核对，且窗内至少一条 AIHOT 证据 | 候选共同来源；再过该来源的连续归档检查 |
| AIHOT 窗内未见，或来源/聚合入口归属不清 | 隔离待核，不纳入正式题池，也不标作 AIHOT 拒绝 |
| `wechat_only`、`wx_*` 微信专用来源、KB/interpret 输入 | 排除于本次评测；生产数据保持不动 |
| 共享主新闻源中的微信公众号原文 | 依来源证据准入，不按域名排除 |
| 来源配置/入口在窗口中改变 | 分段核对身份和覆盖；不得当同一不变源连续贯穿 |

来源证据应能回到 AIHOT 条目、原始响应/页面和 Radar 源配置版本；聚合源需要落到具体原始账号/站点，来源名相似不能替代身份核验。

确认 S 后，保留 S 在合格窗内的**全部过滤前候选**，包括未在 AIHOT 页面找到的新闻。只保留两侧 URL 交集会删除准入与精选本该面对的困难候选，虚增拟合程度。

“AIHOT 至少出现一次”是本次保守的来源准入条件，不是对 AIHOT 全部来源的推断。窗内未出现不证明 AIHOT 从不采这个源；等以后获得证据可以重新准入，但不能事后改变已经报告的题集身份。

## 4. 连续性与完整性按共同来源检查

先从配置与实际启用记录得到每个来源在该窗内应执行的采集槽，再逐槽核查完成状态、来源结果、payload 与依赖。调度频次不能从看到多少 run 反推出来。来源组不同时，完整性结论必须附带 S，而不是只给全站一个绿灯。

- 成功且确为空：是可用的空候选观察，不是漏采。
- 失败、未尝试、未完成、应有而无的槽：是覆盖缺口，不用相邻轮记录填平。
- HTTP 304：只有能追到同配置、验证器与已归档正文版本的依赖才完整；保留依赖闭包。
- payload 损坏、来源配置身份不明、已丢失的旧正文：不进入正式连续窗口。
- 被排除的微信专用源失败不应自动否定共同来源 S 的完整性；反过来，全轮 completed 也不证明 S 每源每槽成功。

现有 [coverage/freeze 运维入口](../../operations/continuous-eval-data.md) 可检查归档及复制依赖；最终评测准入还需共同来源筛选、AIHOT 参照核对和题目派生。当前 `freeze` 整轮复制不是评测范围筛选器，不能把输出目录换个名字就称为合格题集。

记录“抓取观察数”“去重新闻数”“输入版本数”“来源数”“连续小时数/完整本地日数”时分别计数。跨轮同一正文重复出现可以证明持续观察，但不能反复计为新新闻；同 URL 的两版正文不可合并成一条从未存在过的输入。

## 5. 页面参照：哪些能做 gold

| 参照内容 | 可采信方式 | 缺失时的处置 |
|---|---|---|
| 分数/类别/标题/摘要/理由 | 明确页面面、观察时点与字段呈现，API 值经页面映射核实后使用 | 未知不变成 0 或空串；不进入相应语义指标分母 |
| tags | 原始 SSR 的真实标签观察及对应页面可见性，保留观察证据 | `unknown`、明确空集与“该页隐藏”分开；不把 API 缺字段当 `[]` |
| 精选成员 | 该观察窗口/页面完整集合与成员身份 | 只有单条 selected 标记时，不声称重建了精确历史选择事件 |
| 列表顺序/分页/分组 | 可还原完整查询条件、页范围与时点的页面序列 | 仅日级条目集不能推出当轮候选池、排序或漏项真值 |
| 来源/作者/时间/链接、媒体/相关信息 | 可回查具体页面和原文身份 | 无共同参照的面标待核，不以我方当前输出作为 gold |

规范化 AIHOT schema 主要承载 API 字段与 SSR tags 观察，不能默认它已保存所有页面的完整视觉快照、所有截断状态或历史 selected 事件。对日报/热点等共享面的覆盖需另作盘点，本轮未宣称已取得。

外显 AI 分数不是 AIHOT 内部六维评分真值；页面分类不自动提供 `is_opinion` 真值。由我方另做的人工/模型标注只能带自己的来源身份作诊断，不能冒充 AIHOT 参考输出；本轮不预定额外标注预算。

## 6. 从候选到逐条配对

先用不改变文章身份的 URL 归一化生成候选匹配，再逐条核对来源入口、文章身份、输入正文版本和时序。不得因为标题相像或 URL 一致就自动认定“相同输入”。URL 归一化规则与例外需在实际建题时固定，保留归一化前地址。

| 配对状态 | 可以做什么 | 不能据此说什么 |
|---|---|---|
| 同源同身份，双方输入版本与可用时序均有证据 | 逐输入组件比较；在受控状态下做组合归因 | 仍不能推断 AIHOT 未公开内部算法 |
| 同源同文章，但 AIHOT 输入版本不可知 | 标记 `matched-but-input-equivalence-unverified`，做可观测输出拟合并独立分层 | 不能把差异全部因果归于我方 prompt/模型 |
| 同 URL 但不同入口/正文版本/时序冲突 | 隔离冲突，必要时作为独立版本题 | 不能随意选读数更好的一版配对 |
| Radar 候选未匹配到 AIHOT | 留在候选池，记录未匹配原因或未知 | 不能标成 prefilter 真负例 |
| AIHOT 可见新闻缺 Radar 合格 raw | 进入参照覆盖缺口计数 | 不能静默从总体目标分母删除，制造“全部命中” |

即便 Radar raw 早于 AIHOT discovered，也只证明我方已观察到这一版，不能证明它就是 AIHOT 评分时的输入。AIHOT 未公开模型调用时刻/输入时，保留这个不确定性，不制造一个确定调用时间。

## 7. 从同一原始集合派生不同题目

建题不是复制五份 raw。各对象的题引用同一冻结原始观察、版本与参照证据，附加该对象需要的输入选择和期望输出；具体格式留到后续 L2 设计。

1. 列出候选连续窗和共同来源证据，先排除微信专用/T5/旧运行输出。
2. 通过 S × 时间槽的归档审计与 AIHOT 参照审计，冻结两侧证据及 304 依赖。
3. 建立新闻身份、正文版本、事件组与配对状态；保留所有未配对与缺口计数。
4. 在看优化结果之前固定开发、回归与未接触分组；同文章/转载/版本/同事件不得跨组泄漏。
5. 按 [对象卡](objects-and-metrics.md) 派生 O1—O3 单条题、O4 池/序列题和 O5 页面场景题。
6. 对每个题集记录总候选、可配对、各字段可计分、未知、排除和缺 raw 的数量，最后才计算指标。

时间分组和来源分层都要避免同新闻/事件传播到另一组；来源、日期的难度构成也要报告。开发中已经反复读过/调过的历史集不能重新命名为未接触 holdout。未接触样本不足时如实说不足，不随机重切来制造独立性。

完整池题需要额外保留评测窗前的 warm-up、归档成员与有效阶段结果等初态；它们是重放所需上下文，不自动进入计分窗。缺少初态时只能做定义清楚的无历史/受控池实验，不能冒称历史网站复现。

## 8. 当前已知边界，不是实时库存表

2026-09-16 本次会话盘点的 run `20260916T034603.530863Z-49fef538` 有 161 个来源、4,199 条抓取记录，其中 `wx_wechat2rss` 50 条；排除后 4,149 条只是候选记录，不是合格题量。这是带 run 身份的现场快照，不是持续更新的总量承诺，也不是新评测成绩。

[来源选择](../../../src/airadar/sources/sync.py) 以 `enabled=1 AND paused=0` 决定抓取，包含网站所需微信专用源；[freeze](../../../src/airadar/fetcher/raw_capture.py) 复制整个 run。全量归档本身可以合法服务网站，但本次评测派生必须再按本页筛选。

本组文档尚未实现这层派生，没有创建冻结数据集或题集。接续时应先产生实际准入清单和可用量，不把上述一轮数量、旧 HTML 的十四日统计或日后持续采集承诺当作当前可用量。
