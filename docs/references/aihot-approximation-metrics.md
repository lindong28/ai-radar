## A · 逐条拟合指标（`src/airadar/eval/aihot_fit/metrics.py`）

| 指标 | 设闸 | 量什么 |
|---|---|---|
| `ai_recall` | ✅ | prefilter 对 AIHOT 收录过的条目的召回 |
| `category_agreement` | ✅ | 主类逐条一致率（含混淆矩阵） |
| `tag_jaccard_mean` | ✅ | 标签集合的 Jaccard |
| `score_spearman` | ✅ | 我方分 vs AIHOT 分的秩相关 |
| `summary_closeness_mean` / `summary_bigram_jaccard` | ✅ | 摘要的判官贴近度 / 字面重叠 |
| `reason_closeness_mean` / `reason_bigram_jaccard` | ✅ | 推荐理由同上 |
| `selected_auc` | ❌ 明确不设闸 | 我方分预测 AIHOT `selected` 的 AUC |
| `selected_auc_ranked` | ❌ 明确不设闸 | 同上，但用**生产真实排序分**（含类别系数）。2026-09-10 新增 |
| `selected_p_at_k` | ❌ 明确不设闸 | 按天取 top-k 的命中率 |

后三条不设闸的理由写在 `thresholds.json` 的 `_meta.not_gated`：正例只占 2.8%，迭代规模下区间宽到
floor 会低于随机基线。**`selected_auc_ranked` 已加进 `scripts/derive_eval_fit_thresholds.py` 的 `NOT_GATED`，
但 `thresholds.json` 尚未按新代码重新生成**，故该文件目前还没提到它。

**达标线怎么定**：floor 取**迭代规模**（n=300）基线的 CI 下界，不是全量的——规则与陷阱见 ADR-499e
「达标线怎么定：必须与它将被施加的样本量成对」。

## B · 版面构成指标

| 入口 | 量什么 | 关键限定 |
|---|---|---|
| `scripts/eval/measure_curated_composition.py` | 合并多日窗的构成总变差（TV），**两侧都用 AIHOT 的标签** | 见下三条 |
| `scripts/eval/measure_live_composition.py` | **线上真实页面**的构成（读首页内嵌 JSON） | 线上比本地滞后最多 5 小时；首页 90 秒边缘缓存 |
| `scripts/eval/characterize_aihot_categories.py` | 刻画参照物自己的类别抬升 | 其结论已被「控制分数后效应反转」推翻，见 issue 台账 |

**读 B 家族之前必须知道四条**（每条都是踩过的）：

1. **绝对值判不动。** 合并 TV 的零假设（两侧构成完全相同、仅样本量作用）中位约 0.09、95% 分位约 0.16；
   实测 p 值分深度：**生产深度 TV 0.156 → p=0.024（勉强出噪声）；对齐深度 TV 0.128 → p=0.274（判不动）**。
   脚本现在每次运行都打印零假设与 p 值。**配对比较不受此限。**
   （这两个数是 2026-09-10 夹住深度之后重算的；此前那组标着"对齐深度"的读数——含 TV 0.122 与
   p≈0.22——出自一次**没有夹住深度**的运行，已作废，见 issue 台账。）
2. **逐日 TV 饱和于抽样噪声**（参照物自比 ~0.27）。只读 `POOLED`。
3. **截断深度是混淆变量**：我方 40 条/天 vs 参照物十几条。`--depth aihot` 对齐后再比。
4. **跨标注器比较另有地板**：我方分类器与参照物标签的逐条分歧本身值 ~0.13 的 TV。用 `--labels off`
   取只用参照物标签的口径（历史读数都是这个口径）。

## 达标线：逐类占比落进 AIHOT 该类的 95% CI

**用户 2026-09-10 裁定的判据**，取代此前"没有达标线"的状态。为什么不是整页 TV：那个绝对值在当前
样本量下**指不出是哪一类**——相互抵消的偏差在它上面看不见（同一个 0.156 可以由任何一组产生），
而对齐深度下它连"有没有差异"都判不动（p=0.274）。逐类占比换来的是**现在就
判得动**，且每类各自成立才算过——一类超配、另一类欠配可以在 TV 上互相抵消，在这里不行。

    uv run python scripts/eval/measure_curated_composition.py --depth ours --labels off --record

**权威口径是生产深度（`--depth ours`）**，两个理由：目标写的是"**用户可见**的指标"，而用户看到的
就是那 40 条；且它的 n 是对齐深度的 2.6 倍，**判据只在这里有分辨力**（见下零假设）。对齐深度
（`--depth aihot`）留作归因辅助——它分离"深度选择"与"排序质量"，但样本量不够判达标。

**基线读数（2026-09-10，9 个日窗，生产深度，我方 n=234 / AIHOT n=122）**：

| 类别 | 我方 | AIHOT | AIHOT 95% CI | 半宽 | 判定 |
|---|---|---|---|---|---|
| tip | 29.91% | 32.79% | [25.09, 41.53] | ±8.22 | IN |
| model | 18.38% | 31.15% | [23.61, 39.83] | ±8.11 | **OUT −5.24pp** |
| product | 17.09% | 14.75% | [9.54, 22.12] | ±6.29 | IN |
| industry | 22.65% | 13.11% | [8.24, 20.25] | ±6.00 | **OUT +2.40pp** |
| paper | 11.97% | 8.20% | [4.51, 14.43] | ±4.96 | IN |

⇒ **3/5 类落进区间：model 欠配、industry 超配。** 这是这套指标第一次给出**可指认的类别级缺口**——
TV 结构上给不出它（同一个 0.156 可以由任何一组相互抵消的偏差产生）。

**判据自己的零假设**（`verdict_null`，我方构成与 AIHOT 完全相同时 `inside` 取什么值）——
**先读它再读 `k/5`**：

| 口径 | 我方 n | P(5/5) | E[落进数] | 完美页面拿到 ≤3/5 的概率 |
|---|---|---|---|---|
| **生产深度（权威）** | 234 | **0.949** | 4.95/5 | **0.002 ← 真信号** |
| 对齐深度 | 91 | 0.602 | 4.49/5 | 0.102 ← 判不出「差」与「抖」 |

**三条必读限定**：

1. **判据只取 AIHOT 一侧的 CI**（用户原话），因此**不计我方的抽样误差**——我方占比自己的抖动就能
   把我们推出区间。方向偏严而非偏宽；脚本因此把我方自己的 CI 也记进序列行，供分辨"真偏配"与"n 太小"。
2. **CI 宽度就是这个判据的分辨力，逐类不同**：最宽 ±8.22pp（tip）而非最窄那条 ±4.96pp（paper）
   ⇒ **盲区上界是 ±8.2pp**。（本档第一版把最窄那条当成全局，低估 1.7 倍。）
3. **`gap_pp` 说的是"离区间多远"，不是"离 AIHOT 多远"**：model 记 −5.24pp，而离 AIHOT 的实际占比
   是 **−12.8pp**。序列行同时记 `reference_share`，别只读 `gap_pp`。

**「数据数量达标」的定义**（用户 2026-09-10：不上定时评测，改为持续收集到数量达标后离线迭代）：

| 目标：最宽那一类的 CI 半宽 | AIHOT 侧需要的精选条数 | 折算日窗（现有 9） |
|---|---|---|
| **≤ 5pp（下一个里程碑）** | 约 340 | **约 25 个**（≈ 再 16 天） |
| ≤ 3pp | 约 962 | 约 71 个 |
| ≤ 2pp | 约 2217 | 约 164 个 |

取 ≤5pp 作为下一档：它把当前宽度大致减半，且 16 天内到得了；≤3pp 要 2 个月，属于按需再提。

**别把这张表读成"现在还判不了"**：生产深度下判据**已经有分辨力**（P(5/5)=0.949）。更多数据买的是
**更细**——现在查不出小于 ±8.2pp 的偏差，也分不清 industry 那 +2.40pp 是真超配还是抖动。
代价要一并知道：**CI 收窄 ⇒ 判据变严**，所以同一个系统的某一类可能从 IN 翻成 OUT。那不是回归，
读到翻转先看 `n_reference` 有没有变大。
收集靠 `scripts/capture_aihot_daily.sh`（crontab 每日一次）。一次 capture 拉 AIHOT 的整个 **~7 天滚动
窗口**，所以漏一天下次还能补回来；**连续失败超过 7 天才是永久损失**。读它的 rc 之前先看下节第 1 条：
`target_exists` 是"今天 AIHOT 还没推进 canonical 窗口"这个良性稳态，不是故障。

**趋势序列**：`scripts/eval/composition-history.jsonl`（`--record` 追加一行）。用户预期这组读数
**随迭代轮次逐步逼近 AIHOT 的 CI**，而那条趋势只有在读数跨 session 存活时才验证得了——
所以它 git-tracked，且刻意不在 `data/` 下（那里是 runtime-owned，跟踪即破部署）。
只在一次运行**代表一轮迭代**时传 `--record`：探索性对照（`--multiplier paper=1.0` 一类）不进序列。

## 拿这些指标怎么迭代

分两层。**内层有代码和闸，外层只有纪律**——两层都写在这里，是因为外层此前唯一的载体是执行台账
（`plans/<program>/program.md`，`/plans/` 不入 git 且按收口流程会被删除），于是"目标该怎么逼近"这件事
没有 tracked 落点。

**外层（任务级，用户 2026-09-08 指定的方法，与目标同一句话）**：

> 基于长期目标判断现状与目标的 gap → 对问题归因（是哪个模块的产出有问题；问题在上游模块、还是本模块
> 优化不足、还是本模块的设计导致拟合能力不够）→ 针对最可能是根因的模块做实验 → 过程中持续做**可复用**的
> 投资（更多评测数据、记录做过的实验与结果、越来越靠谱的 llm-as-judge）来逼近目标。

目标本身是「在用户可见的那些指标上足够接近 AIHOT」。**「足够接近」自 2026-09-10 起有定义**——见上「达标线」节
（此前长期没有：`thresholds.json` 的 8 条是回归下限、防变差，不是达标线；ADR-499e 明写「达标线本轮不写」）。

**内层（评测台级，权威在 ADR-499e「怎么用它迭代」）**：

| 环节 | 机制 |
|---|---|
| 固定尺子 | 题集 `questions_sha256` + 抽样 `subset_sha256` + 判官身份三者全同才可比，任一不同即拒比 |
| 固定抽样 | 先按 `question_id` 排序再 `random.Random(seed).sample` ⇒ 固定 `--limit/--seed` 即可复现同一子集 |
| 迭代档 | `eval-fit run --limit 300 --seed 7`（约 900 次调用）；理由维度 `--limit 78 --require-reference reason`（参考侧完整总体）；精选排序只有全量 run 才有足够正例 |
| 判官每轮自证 | `judge --calibrate 20` 跑阳性（候选=参考自身）与阴性（候选=另一题的参考），`scale_ok` 三态 |
| 判改善 | 两个 CI **不重叠**才算 improved（旧判据"下界 > 基线点估计"实测假阳性 9.0%，新判据 0.4%） |
| 判回归 | 设闸指标 CI 下界确认低于 floor ⇒ `report` exit 1 |
| floor 怎么定 | **必须与它将被施加的样本量成对**：取 n=300 迭代档的 CI 下界，不取全量的——区间宽度随 √n 收缩，拿全量下界去要求一次 n=300 确认会在**零回归**时开火 |

**节奏（用户 2026-09-10 裁定）：现阶段不上定时评测。** 改为持续收集 AIHOT 数据到「数量达标」（上节那张表），
再基于这批数据做离线评测与优化迭代。所以"A 家族最后一次带 metrics 的 run 是 09-08、`paper: 0.95` 上线后
8 条设闸指标一次没测过"是**已知且被接受的现状**，不是待修缺口——它的修法是下一轮离线迭代时补跑，不是建作业。

**仍然断着的两处**（2026-09-10 实测）：

1. ~~**收集作业在按计划时间系统性失败。**~~ **已修，且原因不是时段——那条假设被实验证伪。**
   `capture_aihot_daily.sh` 在 09-08 与 09-10 都报 rc=2（`ERROR target_exists: refusing to overwrite
   windows/2026-09-08...--2026-09-09...`）。我先归因为"crontab 的 01:37 UTC 太早、AIHOT 还没推进
   canonical 窗口"，并预写了差异预测（更晚时刻手工重跑应拿到新窗口）。**2026-09-10 实测把它推翻**：
   在 cron 时段之后近 9 小时重跑，它照样抓完整个 surface（33 分钟）才在**写入**那一步拒绝同一个
   窗口 ⇒ AIHOT 自己此刻仍把 `09-08→09-09` 定为最新 canonical，**没有新窗口可抓**。
   **真正的缺陷只在判读**：脚本的 SKIP 分支匹配 `existing capture\|already`，而工具打印的是
   `target_exists` / `existing files`，两者都不匹配——于是"今天没有新窗口"这个**良性稳态**被报成
   失败。已改为匹配 `target_exists` 这个机器 token，并加了守护用例（反向变异确认它打得中）。
   **没有数据在丢**：一次 capture 拉 AIHOT 整个 ~7 天滚动窗口，漏一天靠下次成功即可补回。
   （`windows/` 那 6 个 validated 窗口是另一个 artifact，08-21..09-04 的缺口是作业未运行期的历史遗留、
   已不可补。）
2. **归因没有可判状态的台账**：`git grep hypothesis_id docs/` = 0。归因目前是散文叙事，而本任务已记录
   **五次同形错误**（把非随机切片当总体读），事前挡得住那一类的恰好是"取数之前写下差异预测"这一步。

（已修：B 家族头号指标此前无零假设——`pooled_null()` 现在每次运行强制打印。补算后生产深度 p=0.024、
对齐深度 p=0.274。达标线自己的零假设 `verdict_null()` 同理，2026-09-10 第三轮 review gate 报出后补上。）

## 谁在跑这些指标

**评测没有定时作业，这是裁定而非缺口**（用户 2026-09-10）：现阶段只让**数据收集**每日跑，评测按轮次
手工离线跑。`launchd` / `crontab` 里唯一与本体系相关的作业是 `capture_aihot_daily.sh`（01:37 UTC，
当前正系统性失败，见上节）。

已知且被接受的后果：`paper: 0.95` 于 2026-09-10 上线，而 A 家族最后一次带 metrics 的 run 是 09-08 的
`REG-NEW2D-20260907`（全量基线是 09-06 的 `FULL3-20260906`）——**上线之后 8 条设闸指标一次都没测过**，
补跑归下一轮离线迭代。

一次全量 run 的量级：2741 题 × 3 阶段 ≈ 8.2k 次调用；迭代档（n=300）≈ 900 次。评测支出走独立的
`data/eval-fit/llm-usage-eval.db`，不污染生产成本库。

## 当前的硬瓶颈

**参照物 9 个日窗只发布了 122 条精选**，而这个数同时决定三件事：B 家族绝对值有没有意义、达标线各类
CI 有多宽（当前最宽 ±8.2pp）、以及类别偏置能不能拟合并通过留出验证。下一档目标见上「达标线」节的
样本量表（**约 25 个日窗 / ≈ 再 16 天**）。这不是算法问题，是数据积累问题。
