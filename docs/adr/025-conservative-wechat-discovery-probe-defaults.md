# ADR-025：公众号后台发现探测采用低频、小页的临时保守默认

- 状态：Accepted
- 日期：2026-08-13
- 后续澄清：ADR-044 证明本 ADR 所依据的旧 `rate_limited` 记录没有保留 exact `ret`，不能证明微信官方存在 24 小时窗口；1440 分钟始终只是本项目 feasibility 阶段的本地保守默认
- Supersedes：ADR-024 中“约每 2 小时请求一次”和人工 probe 默认抓取 20 篇的部分；不改变其 shadow、保留 Mp2RSS 和切换门槛
- 范围：默认关闭的单账号人工 probe，以及 scheduled canary 启用前的临时保守默认
- 当前配置说明：ADR-029 已将人工授权键改名为 `manual_backend_requests_enabled`；下文旧键名仅记录本决策作出时的配置形状

## 背景

在获授权的微信公众号后台账号上，旧程序将第一次真实 `appmsgpublish` 非成功响应记录为 `auth_required`，二次登录后又将第二次非成功响应记录为 `rate_limited`。失败后同一个 headed 浏览器仍能显示后台首页，只能证明可见后台会话仍在；旧 ledger 没有保存 exact `ret`，旧 parser 又会合并多个业务错误码，因此这些读数不能区分接口频控、参数拒绝或其他平台失败。shadow 数据库没有候选文章，生产 `items` 和 Mp2RSS 均未变化。

本机尚无成功的 `appmsgpublish` 读数，也没有 14 个目标账号的配额、覆盖率或发文峰值读数。公开实现的一手源码表明，现有工具常用每页 5 篇、默认每天一次或遇限流停止到次日；也有实现每页取 20 篇，但同样建议日常每天一次并在限流后停止。这些源码只能说明生态中的工程策略，不构成微信平台 SLA。

## 考虑过的方案

1. 保留每页 20 篇、每 120 分钟一次。单次覆盖较大、发现较快，但与当前真实限流读数和保守运行目标冲突。
2. 每页 20 篇、每 1440 分钟一次。降低请求频率，但在尚无成功 live 读数时扩大单次响应面没有已证实的稳定性收益。
3. 每页 5 篇、每 120 分钟一次。降低单次量但不降低调用次数，不能充分控制主要的限流风险。
4. 每页 5 篇、每 1440 分钟一次，并在限流后停止自动重试。选择此方案作为默认关闭、人工 shadow feasibility 阶段的临时保守默认。
5. 限流后自动 fallback 到 `free_publish`、`publish` 或 `appmsg`。这些端点尚未在本机证明能按任意目标 `fakeid` 返回相同数据；限流后继续请求还可能放大风控，因此暂不采用。
6. 每次通过 headed UI 自动操作“转载”搜索。它适合冷却后做一次协议观测，但依赖 UI 和长期浏览器状态，不作为首版后台发现路径。

## 决策

单账号人工 probe 的默认 page size 从 20 改为 5；成功后的手工再请求间隔从 120 分钟改为 1440 分钟。`rate_limited` 继续作为立即停止状态，不自动重试，也不自动切换其他微信后台端点。

这项选择优先保护获授权登录态和平台限流预算，并明确接受临时代价：在默认关闭、人工 shadow feasibility 阶段，发现延迟最长约 24 小时；若单个目标账号一天发布超过 5 篇，单页结果可能不完整。生产发现仍由 Mp2RSS 覆盖，因此这些代价不影响当前公开数据。

该默认值不是对 14 个目标账号、最终 scheduler cadence、单页峰值覆盖或接口长期稳定性的结论。它只约束当前单账号人工 probe，以及 scheduled canary 启用前的临时保守默认。

## 后果与后续门槛

本决策不会启用 scheduler、不会切换生产发现源、不会取消 Mp2RSS。由于默认配置仍为 `manual_probe_enabled=false`，代码和配置调整本身不会发出微信后台请求。

进入 scheduled canary 前仍必须另行完成：

- 冷却后取得至少一次真实成功 probe；
- 验证一个授权账号依次读取 14 个目标账号时的实际配额和限流行为；
- 根据实测发文峰值实现有界分页，或证明选定单页容量足够；
- 实现跨进程重启仍有效的持久当日熔断；
- 再根据覆盖率、发现时效与限流预算决定正式 cadence。

上述门槛未完成前，不得启用 scheduled canary。多端点 fallback 仍属未验证候选，若后续采用，需用真实响应证明任意目标 `fakeid` 的等价语义后重新评审。
