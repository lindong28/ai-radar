# ADR-20260906-7c31：网站排序改用拟合参照站点的权重，并取消来源分层系数

- Status: accepted
- Date: 2026-09-06

## Context

[ADR-20260905-499e](20260905-499e-aihot-reference-fit-eval-system.md) 建立了以 AIHOT 历史输出为参考输出的拟合评测体系，但明确把**生产排序留在原地**：当时按 AIHOT 的 `selected` 拟合出的权重没有通过换 seed 的检验（78 个正例撑不起 126 个候选向量的搜索），因此 `AIHOT_FIT_WEIGHTS` 只用于度量、`DEFAULT_WEIGHTS` 不动。

2026-09-06 有两件事改变了这个判断。

其一，刻画参照物的决策函数后发现打分器缺一个维度（读数见 `docs/issues/aihot-fit-eval.md` 的 ISSUE-FIT-19）：AIHOT 打的是**事件重要性**而非内容有用性——分数最高的 18 条里 14 条是同一个收购案，其中一条正文只有一个链接、仍得 93 分——而我们五个维度问的全是这条内容本身如何。加一个 `significance` 维度后，同一批题的拟合度 0.5275→0.5915（配对），该维度单独 ρ=0.6234，高于任何既有维度。

其二，拟合的对象换成了 AIHOT 的 **0-100 分数**而不是它的 `selected`。这一侧数据充足（2741 条配对 vs 78 个正例），且此前就已通过五 seed 留出验证。

用户在拿到实测读数后裁决：采纳该维度，并把生产排序换成拟合权重。

## Decision

`DEFAULT_WEIGHTS` 与 `AIHOT_FIT_WEIGHTS` 合并为同一个向量——density 0.40 / authority 0.10 / significance 0.50，其余三维为 0——并取消来源分层乘数。逐项依据写在 `src/airadar/curator/weights.py` 的注释里（那是使用现场，不在此复述）：为什么三个维度权重为 0、为什么乘数是取消而不是反向调参、拟合与留出的读数。

`Weights` 因此多两样东西：`significance` 字段（默认 0.0），以及 `uses_tier_multiplier` 布尔（默认 False）。后者取代了原来那个 ad-hoc 的模块级常量 `AIHOT_FIT_USES_TIER_MULTIPLIER`——"这套权重用不用分层乘数"是权重向量自身定义的一部分，不该是调用方每次自己记得传对的东西。

`weighted_score` 同时改变一个语义：**一行没有的维度按缺失处理**（从加权中剔除、其余权重放大回原总和），而不是按 0。因为每次精选都会从 `numeric_json` 重算全部历史行，而 `significance` 之前的行没有这个字段；按 0 处理会给整个存量档案施加一个系统性惩罚，且任何测试都看不见——每条新行都是对的。五个既有维度仍然必填，且不论其权重——第一版把这道守卫写成只查有权重的维度，于是在拟合向量下实际只要求 density 与 authority 两维，一个不再产出 relevance / recency / engineering 的 provider 会静默通过；那正是这道守卫要抓的事。它们自第一次打分起就一直有，缺失是缺陷而不是历史。

## Consequences

- 与 AIHOT 打分的相关度：生产排序 0.4502 → 0.6286（留出 0.6331，sd 0.0118，五个 seed 挑出同一向量）。
- **精选没有被伤到**，这是换向量最该问的那个读数：同一批 2741 条上 `selected_auc` 由旧排序向量的 0.7907 变为新向量的 0.7878，差 0.003，远在该指标的区间 [0.7382, 0.8349] 之内。ADR-499e 当初冻住生产排序，正是因为**按 `selected` 拟合**的权重换 seed 就崩；本次换的是**按分数拟合**的向量，分数侧 +0.036、精选侧持平，那条顾虑不成立。两个数都由同一 run 的存储信号离线重算得出（`FULL3-20260906` 跑在权重改动之前，其记录的分数用的是旧向量），是同一批数据上的算术，不是重跑。
- 读者可见：X/Twitter 那一层（T1.5）不再被乘数压低、T1 不再被抬高；"这件事有多大"主导排序。CHANGELOG 已同步。
- 我方原有的编辑立场（工程可用性优先、偏好一手来源分层）在排序中不再体现。这是用户明示的取向——"一切以拟合 AIHOT 作为最高优先级"——不是推断。值得日后加回来的部分记在 issues 里。
- **存量文章的展示分会同时改变**，这是部署那一刻就发生的事：`presentation/summary.py` 对每一条时间线条目用当前权重现算分（精选条目随后被存好的校准分覆盖，非精选条目显示的就是这个现算值）。而 `significance` 之前的行没有那个字段，走的是「剔除并重新归一」这条估计式，新行走三项式，两者在同一个列表里互相排序。实测偏移：均值 −0.130、sd 0.805，16.2% 的行移动超过 1.0 分，2.4% 超过 2.0 分，与真值的 Spearman 0.9286。**没有系统性偏袒**（重新归一相当于把 significance 补成该行 density/authority 的加权均值，这两个分布在本批数据上相近），但噪声不小、且在头部略吃亏。回填存量行的 significance 会消除它，本轮未做。
- 拟合对象仍只有 AIHOT 的分数一侧。**精选（selected）一侧仍未拟合**，理由同 ADR-499e，未变。
- `significance` 由渲染同一个提示词的四个 provider 产出。**不产出它的路径有三条**，不止一条：`heuristics` provider；`AI_RADAR_SCORER=codex_gpt_mini`（它无条件走启发式）；以及那四个 provider 自己在 `DEEPSEEK_API_KEY` 与 `ARK_API_KEY` **都不存在**、或 `AI_RADAR_FORCE_HEURISTIC` 置位时的降级（注意触发条件是环境变量缺失，不是 API 报错——402 会抛异常记成 error 行，不产生启发式行）。
- **降级路径下的排序值得单独知道**：启发式打分的 authority 是 tier 查表常量、density 基本是正文长度的线性代理，重新归一后这类行的分等于 `0.8·density + 0.2·authority`，也就是排序完全由「正文长度 + 来源分层」两个确定性量决定并被放大 2 倍。实测取值区间 4.72–8.72，其中「长正文 + T1 来源」落在 LLM 打分行的第 98.9 百分位。改动前它至少还要与 recency 0.30、relevance/engineering 0.20 摊薄。这是降级形态、不是常态路径，但它的失败样子是「分数看起来正常且偏高」，没有任何告警——已记入 issues。
