# ADR-059：两个微信来源并行运行，按跨源文章身份去重

- 状态：已接受
- 日期：2026-08-20
- 相关：`plans/20260816-mp2rss-replacement/`（TASK-008）、[operations/wechat-ingestion.md](../operations/wechat-ingestion.md)

## 背景

微信公众号发现层一直由付费的托管服务 Mp2RSS 独家承担。2026-08-17 起本机部署了自建的 Wechat2RSS 作为候选替代，两者做了三天只读影子对比，但候选方从未进入生产。

影子读数说明**两个源互有漏文**，谁都不是另一个的超集（2026-08-20 读数，89,760 轮采样）：

| 方向 | 条数 |
|---|---|
| 自建源有、Mp2RSS 没有 | 376 |
| Mp2RSS 有、自建源没有（发布于自建首抓之后且已超 24 小时） | 26 |

因此「直接切换」会立刻丢掉那 26 条所代表的持续漏文（约 9 条/天，集中在量子位、AI科技评论这类高频账号），而「继续只读观察」则一直拿不到那 376 条。用户就切流时机做出选择：**先双跑再决定停不停 Mp2RSS**，理由是订阅费已经是固定支出、退不回来，而「切换时不丢不重复」这件事无论何时切都得先做出来。

## 决策

把自建源接成第二个生产微信来源 `wx_wechat2rss`，与 `wx_mp2rss` 并行，生产 `items` 取两者并集。**Mp2RSS 不停用**——停用是之后另一个独立决定，本 ADR 不覆盖。

同一篇文章不得产生两条 `items`。既有去重（`fetcher/dedup.py`）按 URL 与正文哈希、作用域限于单个 `source_id`，两条都识别不出跨源重复：两个源给同一篇文章的 URL 没有公共子串（Mp2RSS 出短链 `/s/<token>`，自建源出长链 `?__biz=…&mid=…&idx=…&sn=…`），正文也来自不同渲染方。

因此新增一层**跨源身份**，只对 `kind='wechat'` 的来源生效，在 INSERT 之前判定：

```
账号（items.author） + 归一化标题 + |发布时间差| ≤ 5 分钟
（仅匹配 enabled 的来源，且排除条目自己所属的 source）
```

命中即丢弃后到的那一条，**谁先到留谁**。

## 为什么是这三个字段

**为什么不能用 URL 或正文**：见上，两者在两个源之间都没有可比性。

**为什么标题必须配一个时间窗**：纯标题键会误并真实文章。生产库 3272 条微信条目里有 **26 对**同账号、同归一化标题的不同文章——招聘启事、会议推广隔一段时间再发一次。把它们并掉就是真丢文章，比例约 0.8%。

**为什么窗口是 5 分钟**：两个分布之间有很宽的空隙，5 分钟落在中间，离两边都远。

| 读数 | 值 | 样本 |
|---|---|---|
| 同一篇文章在两个源的 `pubDate` 差 | 中位 13 秒、p90 54 秒、**最大 58 秒** | n=118 |
| 同账号真实重发同标题的最近间隔 | **3.33 小时** | n=26 对 |

即窗口取值距上界 5 倍、距下界 40 倍。这两个数各自都是量出来的，不是从"看起来够用"推的。

**归一化只折叠两个 renderer 实测会不一致的部分**：NFKC + 空白折叠 + casefold。两侧都出现的 126 篇里，125 篇原始标题逐字相同，唯一的例外差一个 U+00A0——标点差异为 0。初版还额外剥离了标点，那折叠的是没有人产生的噪声，代价是把真正不同的标题并掉（`报告：1.0！` 与 `报告10` 都会塌成 `报告10`），而这里的误并会永久丢掉一篇文章。同理不做词干化或截断。

## 被否的方案

**按 `__biz + mid + idx + sn` 四元组做身份。** 这是微信自己的文章身份，最准确，但只有长链带这四个值；Mp2RSS 的短链要额外发一次 HTTP 请求解析才能得到，而去重发生在入库前、每轮每条都要做。四元组仍然被记录下来用于影子对比，只是不作为生产去重键。

**始终以 Mp2RSS 的链接与正文为准。** 会放弃双跑最直接的收益——延迟自动取两者更快的那个。而且摘要在第一次入库时就按当时的正文生成了，后到的一方覆盖正文并不会重跑摘要，结果是链接与摘要来源不一致。代价换来的只是站上链接形态统一。

**订 14 个逐账号 feed 而不是一个合集。** 合集 `/feed/all.xml` 全局上限 50 条，逐账号 feed 各 20 条，后者上限更宽、A7 告警也能精确到账号。但按当前约 20 篇/天的产出、pipeline 每 15 分钟一轮，50 条约合两天缓冲，上限吃不到；代价却是 `sources.toml` 多 14 行、每轮多 13 次 HTTP、`/sources` 页面多 14 行，且其中低频账号会长期落在 A7 的「无法评估」桶里。

## 两处连带改动

**长链不再送去抓正文。** 自建源的 feed 自带 `content:encoded` 全文（实测 50/50 条，5–11k 字符），而内置 Playwright 打开 `?__biz=` 长链会被导到 `wappoc_appmsgcaptcha`，三次有界重试后一无所获。不跳过的话，每轮 50 条长链各付三次验证码重试。跳过不损失正文——正文本来就在 feed 里。

**微信文章 URL 原样保留。** URL 规范化原本会重建 query 串，把 base64 的 `__biz=…==` 编码成 `%3D%3D`。微信接不接受这种形态**没有证据**：`curl` 对两种形态给出完全相同的读数（都 302 到「未知错误」），区分不了。而这个 URL 正是读者点的那个链接，所以不做无谓改写。既有 3278 条微信条目的 URL 全部不带 query，改动不影响已存条目。

## 后果

- `/wechat` 的原文链接与正文来源变成短链、长链混合，取决于哪一侧先发现该文章。两种链接在真实浏览器里都能打开。
- **两个来源的入库计数不再可比。** 先到的建条目、后到的被丢弃，计数反映的是抢到手的次数而不是覆盖率。A7「来源静默」逐源判定的阈值取该源自身近 30 天节奏，会自校准；但读这些数字的人必须知道它们衡量的不是覆盖率。覆盖率仍由 `plans/20260816-mp2rss-replacement/tools/shadow_compare.py` 直接从两个 feed 测量，它不读生产库，不受去重影响。
- 来源契约放开了「只能有一个微信来源、且必须是 Mp2RSS」的硬编码，改为按 `required_env` 与 `fetch_url` 自洽配对逐个校验，并禁止两个微信来源复用同一个环境变量。同时收窄一处相关行为：未设置的环境变量**只对显式声明 `optional = true` 的来源**才静默跳过，其余仍报错中断加载——此前这个跳过是按环境变量的名字硬编码的。
- **停用其中一个源有两面代价**，取舍与重新启用前的清重步骤见 [operations/wechat-ingestion.md](../operations/wechat-ingestion.md)「停用其中一个微信源时会发生什么」，取舍本身记在 [issues/general.md](../issues/general.md)。
- 停用 Mp2RSS 仍被两件事挡着，都记在该 plan 的 ISSUE-015：自建源的持续漏文，以及 Mp2RSS 实际供稿 21 个公众号而自建部署只订阅了 14 个。
