# Summary Agent 设计文档

## 1. 角色定位

Summary Agent 是个人知识管理助手中的内容处理组件。它接收用户保存的文章，输出结构化总结，服务于以下场景：

- **快速分流**：用户保存了大量文章但没时间逐篇精读。Summary Agent 帮用户在 30 秒内判断一篇文章是否值得深入阅读、哪些段落最值得看。
- **知识萃取**：从文章中提取可复用的认知和可动手实践的方法，形成用户的个人知识库条目。
- **检索支撑**：输出的关键词和结构化字段，为后续的知识检索和关联推荐提供索引。

**核心假设**：用户不是在"阅读文章"，而是在"管理知识"。Summary Agent 的产出不是文章的缩写版，而是从文章中提炼出的、面向用户目标的结构化知识卡片。

---

## 2. 输出内容选择原则

### 2.1 核心取舍：召回率 vs 有用率

内容总结天然存在一组对立的张力：

| 维度 | 偏向高召回 | 偏向高有用 |
|------|-----------|-----------|
| 表现 | 总结长、信息全、不遗漏 | 总结短、信息精、无噪声 |
| 风险 | 淹没在无关信息中，用户不看 | 遗漏关键信息，用户错过价值 |
| 极端 | 复制原文 | 一句话结论 |

**Summary Agent 的选择：偏向高有用，以"用户拿到后能做什么"为选择依据，容忍对原文信息的主动丢弃。**

理由：

1. **用户瓶颈是处理量，不是信息获取**：在个人知识管理场景中，用户的瓶颈不是"找不到信息"（原文始终可回溯），而是"信息太多处理不过来"。Summary 的价值在于降低认知负荷，而非保全信息量。

2. **Summary 是多步信息获取的第一步，不是唯一一步**：Summary Agent 的产出是用户与知识管理助手交互的起点。用户看到总结后，可以针对感兴趣的条目向助手追问，获取更深层的细节。因此，Summary 的职责不是一次性给全信息，而是准确地暴露高价值的"入口点"——让用户知道这篇文章里有哪些值得深入的方向。

这一设计假设对实现和评测有直接影响：
- **实现**：每个输出条目应当提供足够的上下文让用户判断是否值得追问（如给出关键数据点或方法名称），但不需要展开全部细节。
- **评测**：Summary 的关键失败模式不是"细节不够"，而是"入口点缺失"——某个高价值方向连一句提及都没有，用户根本不知道可以往那里追问。
- **优化**：在召回率和有用率的取舍中，应优先确保高价值方向的入口点不遗漏（召回），然后在此基础上控制每个入口点的信息量（有用率）。

### 2.2 选择原则（按优先级排序）

以下原则相对稳定，用于指导具体输出内容设计的迭代优化：

**原则 1：可操作优先于可知道**

> 用户能拿去做实验、写代码、改方案的内容 > 增长见识但不影响行动的内容。

具体表现：
- 文中给出了具体策略/参数/流程 → 保留
- 文中只给了方向性描述（"我们做了优化"）→ 压缩或丢弃
- 文中给了可对标的数据（benchmark 分数、性能对比）→ 保留关键对标点，不保留完整表格

**原则 2：独特优先于常规**

> 读者不知道的、反直觉的、区别于常见做法的内容 > 业内通识、常见实践。

具体表现：
- 原文提出了新做法且给出对比基准 → 保留
- 原文描述的是行业标准做法 → 丢弃（即使篇幅很大）
- 原文给出了踩坑经验或反直觉的工程发现 → 保留

**原则 3：具体优先于抽象**

> 有数字、有步骤、有条件判断的内容 > 概括性的、概念层的描述。

具体表现：
- "效果从 55.3% 提到 62.0%" → 保留
- "效果有显著提升" → 丢弃
- "超过 32K 时触发 Discard-all" → 保留（有明确触发条件）
- "上下文长了之后需要管理" → 丢弃

**原则 4：条件性收录**

> 某些类别的内容只在满足特定条件时才收录，否则整段跳过。

这是控制召回率膨胀的关键机制。例如：
- "产品动态"仅在文中有明确的落地形态（产品名 + 功能描述）时才收录
- "跑分数据"仅在涉及与用户关注领域直接相关的对标点时才收录

**原则 5：面向用户画像筛选**

> 同一篇文章，面向不同用户画像的总结内容应该不同。选择内容时始终锚定目标用户的角色和工作场景。

用户画像支持**分层身份**：一个用户可以有多个身份层级（如"主要：研发者"+"次要：产品探索者"），每个层级有各自的关注领域和"可操作"定义。画像过滤不是二元的（保留/丢弃），而是**分层标记**：

- 匹配主要身份（层级 1）→ 标记为 primary，完整保留
- 匹配次要身份（层级 2+）但不匹配主要身份 → 标记为 secondary，保留但降级处理
- 不匹配任何身份 → 丢弃

分层标记如何影响各模块的输出，见 Section 3.2 各模块的选择算法。画像文件存放在用户的知识库目录下（`data/summary_agent/<user>/persona.md`），每个用户一个文件。画像文件的 schema 见 Section 4.2。

### 2.3 长度控制准则

- 总结不是越短越好，而是**每一句都有存在的理由**。
- 无信息量的修饰语、过渡句、重复表述应全部去掉。
- 输出长度应与文章的"可操作信息密度"成正比，而非与原文长度成正比。一篇 5000 字但只有一个可操作点的文章，总结可以比一篇 2000 字但处处是干货的文章更短。

## 3. 当前输出内容设计

以下是 Summary Agent 当前版本的输出结构设计。这是选择原则的一种具体实现，随着使用反馈和评测结果可以迭代调整。

### 3.1 输出结构总览

| 模块 | 必选/条件 | 作用 | 对应原则 |
|------|----------|------|---------|
| 文章概况 | 必选 | 1-2 句话概括文章性质和范围，支持快速分流 | 服务于"快速分流"场景 |
| 独特亮点 | 必选 | 筛选出区别于常规做法的核心发现 | 原则 2（独特优先） |
| 产品方向洞察 | 条件 | 仅在文中有明确落地形态时出现 | 原则 4（条件性收录） |
| 可动手实践 | 必选 | 可操作的方法/策略/工具 | 原则 1（可操作优先） |
| 可复用认知 | 必选 | 跨场景可迁移的认知模型 | 原则 1 + 原则 3 |
| 关键词与分类标签 | 必选 | 细粒度关键词用于检索，粗粒度分类标签用于跨文章索引和过滤 | — |
| 价值判断 | 必选 | 帮用户决定是否深入阅读 | 服务于"快速分流"场景 |

### 3.2 各模块详细设计

#### 3.2.1 文章元数据

文章的基础元数据（标题、来源、URL、保存时间）不作为输出文件中的可见章节，而是存储在知识库索引（`index.json`）的 `metadata` 字段中，用于溯源和检索。

#### 3.2.2 文章概况

用 1-2 句话概括文章的性质、主题和范围。为后续所有结构化模块提供上下文，让用户在阅读详细条目前就知道这篇文章"是什么"。

**选择算法**：
1. 识别文章的体裁（技术报告解读、经验分享、访谈对话、产品发布等）
2. 提炼文章覆盖的核心主题（1-2 个）
3. 用一句话组合体裁 + 主题，必要时补充范围限定

**写作约束**：
- 严格控制在 1-2 句。这是最高层级的入口点，不是摘要。
- 描述文章"是什么"，不评价文章"好不好"（评价在"价值判断"模块）。
- 避免罗列具体内容点（具体内容在"独特亮点"等模块展开）。

**示例**：
> 一篇关于 GLM-5 技术报告的逐章解读，覆盖架构改动（DSA 稀疏注意力、MLA + Muon Split）、后训练全流程（SFT → 多阶段 RL → 蒸馏）、Agent 环境构建、评测跑分和产品落地。

#### 3.2.3 独特亮点

从文章中筛选出"读者大概率不知道的"、"区别于常见做法的"发现或方法。

**选择算法**：
1. 遍历文章的主要段落/论点
2. 对每个论点判断：这是行业通识还是新发现？
   - 判断依据：是否给出了与已知做法的对比、是否有反直觉的数据、是否提出了新的方法名称
3. 保留判定为"新发现"的条目
4. 每个条目用一句话描述做法 + 给出文中的关键数据作为支撑

**数量控制**：通常 2-4 条。超过 4 条说明筛选标准不够严格。

**示例**（来自 GLM-5 文章）：
> - **搜索 Agent 的上下文管理给了可直接照抄的策略**：`Keep-recent-k`（只保留最近 5 轮完整内容，旧工具结果折叠；文中给出效果 55.3%→62.0%）+ 超 32K 触发 `Discard-all`。

#### 3.2.4 产品方向洞察

**收录条件**：文中有明确的产品名称 + 功能描述。仅描述趋势或方向但无具体产品形态的不收录。

**选择算法**：
1. 扫描文章中的产品/工具提及
2. 筛选有"产品名 + 具体功能"的条目
3. **分层画像过滤**（同 3.2.5 的机制）：匹配层级 1 → primary（无标注），匹配层级 2+ → secondary（标注该层级的身份标签，如 `[产品]`），不匹配 → 丢弃
4. 用一句话描述产品形态

#### 3.2.5 可动手实践

这是 Summary Agent 输出中最核心的模块，直接体现"可操作优先"原则。

**选择算法**：
1. 从文章中提取所有具体的方法/策略/工具
2. **分层画像过滤**（见原则 5）：
   - Pass 1：匹配层级 1（主要身份）的关注领域 → 标记为 primary
   - Pass 2：匹配层级 2+（次要身份）但不匹配层级 1 → 标记为 secondary
   - 不匹配任何层级 → 丢弃
3. 对通过过滤的条目，使用**对应层级的"可操作"标准**评估可动手程度。判断锚点是"用户能否行动"，而非"文章提供了多少细节"：
   - 用户凭自身能力和工具（包括 coding agent）**可以直接动手**做这件事 → ✅可实现
   - 用户能理解方向，但需要补充关键信息（定价、API、性能数据等）才能决策或动手 → ⚠️需补充
   - 文中仅提及名称，无法形成可操作的行动 → 不收录

   注意：评估"可实现"时要考虑用户的**完整能力栈**，包括 coding agent 等工具。例如，一篇产品介绍文章虽然没有给出实现步骤，但如果用户可以用 coding agent 快速搭建 MVP 来验证产品假设，这就是"可实现"而非"需补充"。

   **资源导航**：文章列举了具体的工具/库/开源项目，且提供了足够信息让用户找到并使用它们（名称 + 用途描述 + 可推断的获取方式），即使文章本身的分析深度有限，"下载体验""阅读源码学习"本身也是可操作的实践。但此类实践项需用户凭自身判断确认是否有学习价值，标注为 ⚠️需补充（需评估具体工具的质量和适用性）。
4. 保留"可实现"和"需补充"的条目
5. 以表格形式呈现：目录点 | 你可以做什么 | 可动手程度
   - primary 项目直接列出（无标注）
   - secondary 项目在目录点前标注该层级的身份标签（如 `[产品]`，从 persona.md 中每个层级的 `**标签**` 字段读取），排在 primary 项目之后
6. 为 primary 中最有价值的 1-2 个条目补充**最小实验工作流**（3-5 步骤）。secondary 项目不展开工作流。
7. 标注文中是否提供了可直接复制的代码/Prompt

**数量控制**：表格通常 3-5 行（primary + secondary 合计）。工作流通常 1 个（仅 primary）。

#### 3.2.6 可复用认知

提取跨场景可迁移的认知——不是具体方法，而是"做了这个实验/看了这篇文章后，你的判断框架应该如何更新"。

**选择算法**：
1. 识别文章中的因果关系陈述（X 导致 Y、做了 A 发现 B）
2. 判断该因果关系是否可泛化到用户的工作场景
3. 用一句话描述该认知，避免特定于原文的术语

**数量控制**：通常 2-3 条。

**示例**：
> - 搜索任务里工具调用历史会持续累积、上下文变长，性能会下降；上下文管理策略会显著影响最终效果。

#### 3.2.7 关键词与分类标签

**关键词**：用于知识库检索和文章关联，是文章级的细粒度术语。关键词同时出现在输出文件（供用户阅读）和 `index.json` 的 `metadata.keywords` 字段（供程序化检索）。

**选择算法**：
1. 从独特亮点和可动手实践中提取核心概念
2. 使用 hashtag 格式
3. **归一化**：扫描 `index.json` 中已有的 `metadata.keywords` 列表，如候选词与已有词指代同一概念（中英文对、近义表述），复用已有形式。偏好规则：已有形式优先；中文优先（用户主要用中文检索）
4. 偏向具体术语（`#Keep-recent-k`）而非泛化类别（`#AI`）

**数量控制**：5-10 个。

**分类标签**：跨文章的粗粒度主题分类，用于索引和过滤。标签词汇表及添加规则维护在 `agents/summary-agent/docs/tags.md`。

**选择算法**：
1. 从 `agents/summary-agent/docs/tags.md` 读取现有标签词汇表（按维度组织：构建、评测、进化、应用方向）
2. 从文章的独特亮点和可动手实践中识别 2-3 个主题域，先确定维度再在维度内匹配标签
3. 优先复用已有标签；仅在现有标签无法覆盖时新建（新建时同步更新 `tags.md`，归入对应维度）
4. 标签格式为名词短语（如 `Agent架构`、`评测设计`），不加 hashtag

**数量控制**：2-3 个。

**输出格式**：
```
### 🏷️ 关键词
`#术语1` `#术语2` ...

**分类标签**: `标签1` `标签2` `标签3`
```

#### 3.2.8 价值判断（criteria v2）

帮 AI 雷达读者判断原文是否值得占用阅读时间。推荐等级衡量的是**阅读价值**，与文章是否值得保存到个人知识库分属两个独立判断轴。

**包含字段**：
- **推荐等级**：必读 / 值得一看 / 可跳过（附一句话理由，明确说明信息增量、实现细节/深度或时效相关性中哪些支撑该档位）
- **最值得看**：指出原文中最值得精读的段落
- **适合场景**：描述什么情况下这篇文章的内容最有用

**选择算法**：
1. 先忽略文章是否有 primary / secondary `✅可实现` 项，仅从 AI 雷达读者的阅读收益评估原文。
2. 独立评估三个维度：
   - **信息增量**：相对于熟悉 AI 行业动态的读者，是否提供新事实、新数据、新方法或足以改变既有认知的证据；重述已知趋势、只有宣传口号或缺少证据的观点增量低。
   - **深度 / 实现细节**：是否给出机制、因果链、技术方法、关键数据、取舍或可复现细节；篇幅长、信息点多或有操作步骤，不等于有深度。
   - **时效相关性**：信息是否对读者当前的技术、产品或行业判断有直接影响；“刚发布”本身不等于高时效价值，经典但足够深的内容也不因不新而自动降档。原文没有可靠的发布时间或其他时间锚点时，不猜测新旧，且不得用该维度作为升档证据。
3. 综合三个维度判档，以“读原文的额外收益是否抵得过时间成本”为最终问题。默认档位是“可跳过”；只有原文保留了摘要无法安全压缩的实质证据、论证或实现细节时才升档。“还有一些例子/数据/叙事细节”不足以升档。

| 等级 | 用户行动 | criteria v2 判断标准 |
|------|---------|---------|
| **必读** | 安排时间精读原文对应段落 | 阅读价值显著高于普通优质文章：信息增量和深度两项均强，或其中一项很强且时效相关性也强；原文的关键证据、论证或实现细节对当前判断至关重要，无法由摘要代替 |
| **值得一看** | 先看摘要，再按“最值得看”定向阅读原文 | 至少一个维度强，并且原文含有会实质改变理解、决策或复现结果的证据/论证/实现细节，无法被摘要安全代替；仅有中等维度的累加、额外事例或更完整叙事不足以进入此档 |
| **可跳过** | 不投入原文阅读时间 | 默认档位。内容主要重述已知信息、停留在口号/新闻摘编层、缺少支撑细节、与 AI 雷达读者当前判断关联弱，或摘要已安全承载其核心新信息；单个新观点或数据点若已被摘要说清，仍属此档。即使存在可操作项或可转化的产品场景，也不因此自动升档 |

**分布校准指引**：在题材和时间范围有代表性的文章集合上，目标分布为 **必读 5-15%、值得一看 20-40%、可跳过为其余且应占多数**。这是防止档位通胀的校准目标，不是对单篇文章或每个小批次强行凑比例；单篇仍必须仅依上述阅读价值证据判定。

**KB 保存轴（语义保持不变）**：`save_decision` 仍按个人知识库用途判断，不与 criteria v2 的阅读价值档位合并。

- 有 primary `✅可实现` 项：保存。
- 推荐等级为 `必读` 或 `值得一看`：保存。
- 推荐等级为 `可跳过` 但有 secondary `✅可实现` 项：保存。
- 推荐等级为 `可跳过` 且无 meaningful `✅可实现` 项：不保存。

- "最值得看"指向信息增量、论证深度或实现细节最密集的原文段落
- "适合场景"从用户画像出发，描述具体的工作场景（可覆盖多个身份层级）

## 4. 设计边界与后续扩展

### 4.1 当前版本不做的事

- **不做观点评价**：不评判文章的论点是否正确、立场是否合理。Summary Agent 是信息萃取工具，不是评论员。
- **不做跨文章关联**：当前版本处理单篇文章。跨文章的知识图谱和关联推荐由知识管理助手的其他组件负责。
- **不做个性化排序**：当前版本的输出结构对所有文章一致。后续可根据用户的历史阅读偏好调整模块权重。

### 4.2 用户画像

用户画像是 Summary Agent 的输入配置，影响原则 5（面向用户画像筛选）在每个模块中的判断。不同画像会导致相同文章产生不同的总结内容。

**存储位置**：`data/summary_agent/<user>/persona.md`，每个用户一个文件，位于该用户的知识库目录下。

**画像文件 schema**：

```
# 用户画像

## 长期目标
<用户的长期方向，相对稳定，很少变化>

## 身份层级
<按当前优先级排序，优先级随阶段演进而变化>

### 层级 1（主要）：<身份名称>
**标签**: <1-2字缩写，用于摘要中标注该身份的内容>
<当前阶段的主要身份>

关注领域: <该身份日常涉及的主题列表>
不关注领域: <明确排除的主题>
"可操作"的判断标准: <该身份视角下什么算可操作>

### 层级 2（次要）：<身份名称>
**标签**: <1-2字缩写，用于摘要中标注该身份的内容>
<当前关注但优先级较低的身份>

关注领域: ...
不关注领域: ...
"可操作"的判断标准: ...

### 层级 N...
```

**各字段对选择算法的影响**：

| 字段 | 作用 |
|------|------|
| **长期目标** | 提供跨层级的整体判断锚点。当层级间的判断存在冲突时，以长期目标为仲裁依据 |
| **身份层级顺序** | 决定 primary/secondary 标记。层级 1 的匹配结果为 primary（无标注），层级 2+ 为 secondary（标注该层级的标签） |
| **标签**（per 层级） | 1-2 字的缩写名称，用于摘要中标注 secondary 内容的来源身份（如 `[产品]`），primary 层级的标签仅作备用 |
| **关注领域**（per 层级） | 原则 5 分层过滤时，判断内容属于哪个层级 |
| **不关注领域**（per 层级） | 原则 5 过滤时，命中任何层级的"不关注"都直接丢弃 |
| **"可操作"标准**（per 层级） | 影响 Section 3.2.5 的可动手程度评估。不同身份对"可操作"的定义不同 |

**演进机制**：当用户的阶段发生变化（如从"技术积累"转向"产品落地"），只需调整层级顺序——把层级 2 移到层级 1 的位置。不需要修改设计文档或 skill。

**当前画像**：`data/summary_agent/dong_lin/persona.md`。当前 reference output 基于此画像的层级 1（Agent 应用研发者）生成。

### 4.3 评测方向

Summary Agent 的输出质量可从以下维度评测：

| 维度 | 含义 | 对应原则 |
|------|------|---------|
| 准确性 | 总结中的事实是否与原文一致 | 基础要求 |
| 有用率 | 总结中的条目有多少对用户实际有用 | 原则 1-3 |
| 遗漏率 | 文章中有价值的信息是否被遗漏 | 召回率维度 |
| 简洁度 | 总结中是否有冗余/无信息量的内容 | 长度控制准则 |
| 可操作性 | "可动手实践"模块是否真的可以动手 | 原则 1 |
